Overview

A single page for the repo's actual working logic

The repository has already converged around a clear shape: deterministic tools, explicit workflow skills, structured outputs, and control-plane abstractions that sit above any single world-model codebase.

01

Train Control

Targets, experiments, stage overrides, ledgers, bundles, lineage, and compare utilities all live in one CLI-first training layer.

02

Native Evaluation

WorldArena handles score-oriented evaluation while ACWM Bench focuses on structure audits, domain constraints, rollout fidelity, and diagnosis-first reasoning.

03

Closed Loop Research

Loop control resolves train outputs into eval inputs, runs ACWM, reads patch plans, and decides whether to continue, converge, block, or request attention.

Important framing

WorldClaw is explicitly positioned as a local research control plane. The older MetaBot platform remains available as an optional adapter layer, but it is no longer the default center of the repository.

Control Plane

From config to patch plan in one loop

The main research path is no longer hidden in random shell notes. It is a visible pipeline with stable contracts and explicit artifacts.

Target + Experiment

`target.json` and experiment specs define the train objective, runtime bindings, dataset assumptions, and stage plan.

Training or Export

Train runners execute setup, train, eval, export, and bookkeeping stages while isolating each iteration's artifacts.

Structured Eval Inputs

`train-result.json` resolves into rollout manifests, action manifests, references, and metrics bundles for ACWM and eval tools.

Diagnosis + Patching

Eval produces summaries, failure modes, oracle status, patch plans, and loop-facing decisions instead of only a scalar score.

Loop Summary + Memory

The controller records loop outcomes and prepares experiment memory so later runs can compare, learn, prune, and recover context.

train-request.json

The loop controller's structured instruction to the training layer.

train-result.json

The canonical bridge from training output into evaluation input resolution.

rollout-manifest.json

Episode, camera, generated path, reference path, horizon, and action binding contract.

action-manifest.json

Action-space metadata and sequence bindings required for ACWM checks.

metrics-bundle.json

Exported metrics sidecars used by metric-backed ACWM suboptions and oracles.

summary.json

Unified human and machine readable summary emitted across train, eval, and loop.

patch-plan.json

Eval-to-train remediation instructions for the next iteration or capability fix.

worldclaw_memory.sqlite

Structured experiment memory for weighting, pruning, and reuse beyond a single run.

Evaluation

Two evaluation tracks, two different research jobs

WorldArena and ACWM Bench are not duplicates. One is an external or benchmark-facing entry. The other is a native diagnosis system built for closed-loop world-model improvement.

WA

WorldArena

Score-oriented evaluation with backend detection, candidate precheck, single-video quick paths, dry-run execution, latest summary, and compare.

video-quality vlm-judge jepa-similarity embodied-task
AC

ACWM Bench

Diagnosis-first evaluation for action sensitivity, long-horizon stability, domain constraints, policy alignment, and patch-plan generation inside the loop controller.

action-sensitivity domain-consistency physics-or-rule rollout-fidelity policy-alignment stability-guard adversarial-actions

Provider adapter boundary

WorldClaw avoids turning into "just a Ctrl-World wrapper" by separating the generic loop core from provider adapters and domain profiles. The current provider is `ctrl-world`, but the structure is meant to accept more world-model backends without rewriting the train/eval core.

Generic loop core Consumes train requests, train results, eval reports, patch plans, and memory records.
Provider adapter Owns preflight, runtime overlay, contract export, and repo-specific integration details.
Domain profile Defines robotics, driving, game, or custom constraint priorities and oracle thresholds.

Current integration status

The current `ctrl-world` integration already supports preflight, worldclaw-side smoke scaffolding, contract export, runtime overlay, and loop artifact isolation.

Known gap right now

Metric-rich ACWM sidecars are still incomplete for some real suboptions. Structure-complete manifests already exist, but richer exported metrics remain the next important integration step.

Get Started

A minimal path into the working surface

These are the repo-native commands that explain the project best. They stay close to the current code layout and do not assume a paper-only workflow.

1. Install the lightweight dependencies

Start with the CLI-first control plane instead of heavy training dependencies. 

python -m pip install -r requirements-lite.txt

2. Inspect train and eval entries

List the supported evaluation modes and resolve a concrete training run. 

python tools/eval/main.py list-entries
python tools/eval/main.py acwm list-suboptions
python tools/train/run.py resolve-run ctrl-world --experiment-id smoke-train-eval --json

3. Plan a closed ACWM loop

Use the provider-aware loop controller to plan a control-plane iteration. 

python tools/loop/run.py plan-acwm \
  ctrl-world \
  smoke-train-eval \
  action-sensitivity \
  --provider-id ctrl-world \
  --preflight-profile smoke \
  --json
Roadmap

What would make this control plane materially stronger

The page should show the repo honestly: real structure already exists, but some pieces are intentionally still advancing from smoke-grade to production-grade research infrastructure.

A

Metric-rich ACWM sidecars

Promote structure-only exports into richer action sensitivity, contact, drift, and policy-alignment metrics for more decisive ACWM loop actions.

B

More provider adapters

Keep the loop core stable while registering additional world-model backends through the provider boundary instead of special-casing every new repo.

C

Memory in the default loop

Move experiment memory from a side utility into the regular train and report flow so the system can truly learn from prior iterations.
